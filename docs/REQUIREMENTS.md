# 프로젝트명: 세종 봉쇄구역 (SEJONG: QUARANTINE ZONE)

## 0. 프로젝트 개요 및 개발 지침

너는 전문 게임 디렉터, 풀스택 게임 개발자, 멀티플레이 서버 엔지니어, 게임 시스템 설계자, 픽셀 아트 UI/UX 디자이너다.

지금부터 GitHub 저장소에 실제 서비스 가능한 **2D 픽셀 기반 온라인 협동 좀비 생존 게임**을 개발한다.

게임은 PC와 스마트폰에서 웹 브라우저로 실행되어야 하며, 별도의 프로그램 설치 없이 친구들과 실시간 멀티플레이를 즐길 수 있어야 한다.

### 참고 게임

좀비고등학교의 스토리 모드, 특히 디비전 시리즈를 게임 시스템의 주요 참고 대상으로 삼는다.

참고할 핵심 요소:

- 2D 탑다운 픽셀 아트
- 상하좌우 4방향 격자 이동
- 대각선 이동 불가능
- 좀비의 탐색 및 추격 AI
- 직업별 공격과 특수 능력
- 작업대를 통한 직업 능력 강화
- 최대 4인 협동 스토리 모드
- 계정 및 로그인
- 서버 채널 선택
- 게임 로비 및 방 생성
- 계정 레벨과 경험치
- 게임 내 상점
- 캐릭터 스킨
- 전투 HUD
- NPC 대화와 스토리 진행
- PC 키보드 조작
- 모바일 가상 조이스틱 및 터치 전투 버튼

참고 게임의 일반적인 시스템과 게임 메커니즘은 참고하되, 원작의 소스코드, 그래픽, 스프라이트, 캐릭터, 사운드, 대사, 맵 구조, 고유 명칭 및 UI 디자인은 복제하지 않는다.

기능적으로 친숙하지만 시각적·서사적으로 독립적인 게임을 제작한다.

### 최상위 목표

**단순히 화면이 표시되는 데모가 아니라 실제로 로그인하고, 친구들과 같은 방에 접속하고, 좀비를 피하거나 전투하면서 스토리를 진행할 수 있는 온라인 게임을 개발한다.**

그러나 처음부터 모든 콘텐츠를 동시에 구현하지 않는다.

실제로 플레이 가능한 작은 버전을 완성한 뒤 단계적으로 확장한다.

모든 개발 설명, 문서, 작업 보고는 한국어로 작성한다.

# 1. 세계관 및 스토리

## 1.1. 기본 배경

배경은 대한민국 세종특별자치시이다.

세종특별자치시의 가상 학교인 '양지고등학교'에서는 비밀리에 생명과학 연구가 진행되고 있었다.

학교 지하에 설치된 연구시설에서는 인체의 생물학적 회복 능력을 향상시키기 위한 정체불명의 감염체 연구가 이루어지고 있었다.

그러던 어느 날 실험이 통제 불능 상태에 빠진다.

시설 내부의 감염체가 탈출하고 연구원과 학교 관계자들이 감염되면서 사태가 걷잡을 수 없이 확산된다.

처음에는 학교 내부에서 발생한 작은 사고로 여겨졌지만, 감염이 학교 밖으로 전파되면서 세종시 전체가 위험에 빠진다.

정부는 감염 확산을 막기 위해 세종시 일대를 봉쇄구역으로 지정한다.

도로가 차단되고 일부 통신망과 전력망이 마비된다.

도심에는 좀비가 돌아다니고 생존자들은 건물과 임시 대피소에 고립된다.

플레이어들은 양지고등학교에서 사건을 경험한 생존자들이다.

다른 플레이어들과 협력하면서 감염의 원인을 조사하고, 봉쇄구역을 탈출해야 한다.

실제 지명과 도시 구조는 배경 모티브로 활용하되, 학교와 연구시설, 사건 및 관련 기관의 행동은 허구의 설정임을 분명히 한다.

## 1.2. 스토리 진행 방식

스토리는 챕터 단위로 진행한다.

각 챕터에는 여러 스테이지가 존재한다.

스테이지별로 다음 요소를 포함한다.

- 독립적인 맵
- 스토리 대화
- NPC
- 미션
- 좀비
- 퍼즐
- 작업대
- 체크포인트
- 탈출 지점
- 클리어 보상

다른 챕터를 나중에 추가할 수 있도록 데이터 기반으로 설계한다.

## 1.3. 챕터 구성

### 프롤로그 — 탈출 불가능한 학교

장소: 양지고등학교

주요 내용:

1. 평범하게 학교에서 하루를 보내던 중 이상 현상 발생
2. 교내 방송에서 긴급 대피 안내
3. 학생들이 좀비로 변하기 시작
4. 교실과 복도를 탐색
5. 최초 좀비 조우
6. 공격 및 이동 튜토리얼
7. 직업 선택 및 첫 번째 작업대 사용
8. 학교의 출입구 확보
9. 학교 탈출

엔딩 연출:

학교 밖으로 나왔지만 주변 도시는 이미 감염으로 무너지고 있다.

구조 신호를 확인한 플레이어들은 도심을 통해 탈출할 방법을 찾는다.

### 챕터 1 — 버려진 도시

장소: 세종시 주거지역과 상업지구를 각색한 도심

- 생존자 수색
- 보급품 확보
- 도로 통제 구역 돌파
- 최초 특수 감염자 등장
- 통신시설 복구
- 구조 신호 송신

### 챕터 2 — 침묵하는 행정도시

장소: 정부세종청사 주변을 모티브로 한 가상 구역

- 행정시설 탐색
- 봉쇄 작전 기록 발견
- 감염체 연구 관련 단서 발견
- 전력 복구
- 강력한 보스 감염체 등장

### 챕터 3 — 금강의 마지막 길

장소: 금강 및 주요 교량 주변을 각색한 지역

- 차단된 교량
- 수로 탐색
- 대규모 좀비 추격
- 생존자 구조
- 탈출 통로 확보

### 챕터 4 — 봉쇄선 너머

장소: 세종시 외곽 봉쇄구역

- 봉쇄선 진입
- 감염 사태의 진실 확인
- 마지막 구조 작전
- 최종 보스
- 봉쇄구역 탈출
- 엔딩 및 후속 이야기 복선

최초 개발 단계에서는 프롤로그만 실제로 제작한다.

나머지 챕터는 데이터 구조와 기획 파일을 준비하고 순차적으로 개발한다.

# 3. 시스템 아키텍처

## 3.1. 전체 연결 구조

사용자 브라우저
↓
게임 웹페이지
↓
Cloudflare Worker
↓
로그인 및 인증 API
↓
D1 사용자 데이터베이스
↓
서버 채널 선택
↓
게임 로비
↓
게임 방 생성 또는 참가
↓
방별 Durable Object
↓
WebSocket 연결
↓
실시간 게임 플레이

## 3.2. 게임 서버

게임 방마다 고유 roomId를 부여한다.

각 방의 게임 상태는 해당 방의 Durable Object에서 권위 있게 관리한다.

관리할 상태:

- 참가자
- 플레이어 위치
- 플레이어 HP
- 직업
- 스킬
- 좀비 위치
- 좀비 상태
- 미션
- 맵
- 아이템
- 작업대 강화
- 게임 진행 단계

클라이언트는 입력을 보내고 서버는 이를 검증하여 실제 게임 상태를 갱신한다.

다른 방의 상태가 서로 섞이면 안 된다.

## 3.3. 서버 최적화

무료 요금제 사용을 고려하여 다음을 구현한다.

- 방별 플레이어 최대 4명
- 상태 변화 중심 메시지 전송
- 적절한 서버 시뮬레이션 주기
- 불필요한 패킷 제거
- 변경 사항 또는 압축된 스냅샷 전송
- 서버 상태 갱신 빈도 조절
- 빈 방 자동 정리
- 비활성 게임 시뮬레이션 중지
- 로비 연결의 WebSocket Hibernation 활용
- 데이터베이스 저장 횟수 최소화
- 접속자 수 및 요청량 모니터링
- 서버 부하 상황에 따른 방 생성 제한

게임 중 활성 시뮬레이션으로 Durable Object의 실행 시간 비용이 발생할 수 있다는 점을 고려한다.

무료 한도가 충분하다고 무조건 가정하지 않는다.

실제 동시 접속자와 메시지 빈도를 기준으로 예상 사용량을 분석한다.

# 8. 이동 시스템

이동 시스템은 게임의 가장 중요한 핵심 기능 중 하나다.

## 8.1. 이동 기본 규칙

- 상하좌우 4방향 이동
- 대각선 이동 불가능
- 한 번에 한 타일 이동
- 이동키 유지 시 연속 이동
- 장애물 충돌
- 이동 중 픽셀 애니메이션
- 방향별 캐릭터 애니메이션
- 이동 명령 서버 검증

플레이어는 논리적으로 정수 격자 좌표를 사용한다.

예:

현재 위치: (5, 7)

오른쪽 → (6, 7)

위쪽 → (5, 6)

두 축을 동시에 변경하는 대각선 이동은 허용하지 않는다.

한 칸 이동하는 동안 렌더링 좌표를 보간하여 움직임을 부드럽게 표현한다.

## 8.2. 이동 속도

권장 초기 설정:

- 기본 이동 간격: 140ms
- 렌더링: 최대 60FPS
- 격자 크기: 32×32

이 수치들은 설정 파일로 조정할 수 있어야 한다.

## 8.3. PC 이동

- W / ↑ : 위
- S / ↓ : 아래
- A / ← : 왼쪽
- D / → : 오른쪽

두 방향을 동시에 입력해도 한 방향만 선택한다.

대각선 이동은 허용하지 않는다.

# 9. 스마트폰 가로 화면 전용 시스템

**이 항목은 반드시 구현해야 하는 최상위 플랫폼 요구사항이다.**

## 9.1. 스마트폰 가로 모드 강제 정책

스마트폰에서는 게임의 모든 화면을 가로 모드에서만 이용할 수 있어야 한다.

적용 범위:

- 로딩
- 타이틀
- 회원가입
- 로그인
- 서버 선택
- 로비
- 방 목록
- 방 생성
- 직업 선택
- 게임 플레이
- 작업대
- 상점
- 스킨
- 프로필
- 설정
- 게임 결과

**세로 모드에서는 어떠한 게임 메뉴나 플레이 조작도 사용할 수 없어야 한다.**

단, 화면 회전을 안내하는 전용 화면은 표시한다.

## 9.2. 세로 모드 감지

스마트폰에서 세로 방향이 감지되면 다음 안내를 화면 전체에 표시한다.

"게임을 플레이하려면 휴대폰을 가로로 돌려주세요."

화면에는 휴대폰 회전 안내 아이콘을 표시한다.

안내 화면 뒤에 있는 모든 게임 UI는 접근할 수 없도록 한다.

터치 및 게임 조작 입력을 차단한다.

진행 중인 입력은 해제한다.

가로 방향으로 변경되면 자동으로 안내 화면을 닫고 정상 화면으로 돌아온다.

플레이 중 세로 모드로 전환되었을 때는 해당 클라이언트의 조작만 중지한다.

멀티플레이 방 전체의 서버 시뮬레이션을 중지해서는 안 된다.

## 9.3. 화면 방향 잠금

브라우저와 기기가 지원하는 경우:

- Screen Orientation API 활용
- 전체화면 진입 시 landscape 방향 잠금 시도
- 기기 회전 감지
- viewport 크기 변경 감지

단, 일부 브라우저에서는 강제 방향 잠금이 지원되지 않거나 사용자의 조작이 필요할 수 있다.

지원되지 않는 경우에도 정상적으로 동작해야 한다.

방향 잠금 API가 실패하면 화면 회전 안내 UI로 처리한다.

**세로 모드 플레이를 허용하는 대체 옵션은 만들지 않는다.**

## 9.4. PC 화면 정책

PC에서는 가로형 게임 레이아웃을 기본으로 하되, 브라우저 창의 크기를 자유롭게 변경할 수 있다.

PC는 스마트폰의 화면 방향 제한과 구별하여 처리한다.

# 10. 모바일 가상 조이스틱

좀비고등학교 모바일 스토리 모드처럼 왼손으로 이동하고 오른손으로 공격하는 조작 방식을 참고한다.

## 10.1. 기본 배치

스마트폰 가로 화면 기준:

- 왼쪽 아래: 원형 가상 조이스틱
- 오른쪽 아래: 기본 공격 버튼
- 공격 버튼 위: 스킬 1
- 공격 버튼 왼쪽: 스킬 2
- 주변 적절한 위치: 상호작용 버튼
- 왼쪽 위: 체력
- 위쪽 중앙: 현재 미션
- 오른쪽 위: 메뉴 버튼

모든 게임 조작 UI는 반투명하게 표시한다.

## 10.2. 이동 방식

가상 조이스틱을 특정 방향으로 움직이면 해당 방향으로 이동한다.

- 위쪽: 위
- 아래쪽: 아래
- 왼쪽: 왼쪽
- 오른쪽: 오른쪽

손을 떼면 이동 입력을 종료한다.

누르고 있으면 이동 간격에 맞춰 연속 이동한다.

## 10.3. 대각선 입력 처리

가상 조이스틱은 원형으로 구현하되, 캐릭터는 반드시 4방향으로만 이동한다.

입력 벡터에서 수평축과 수직축을 비교한다.

절댓값이 더 큰 축을 우선한다.

예:

(0.9, 0.3) → 오른쪽

(-0.8, 0.2) → 왼쪽

(0.1, -0.9) → 위

(0.1, 0.8) → 아래

두 축이 비슷한 경우 갑작스러운 방향 흔들림을 방지하기 위해 히스테리시스를 적용한다.

작은 입력은 데드존으로 처리한다.

한 번의 이동 명령은 한 축의 한 칸 이동만 생성한다.

## 10.4. 조이스틱 모드

두 종류의 조이스틱을 설계한다.

고정형:

- 일정한 위치에 조이스틱 표시
- 중앙으로부터 터치 방향 계산

유동형:

- 왼쪽 조작 영역을 터치하면 해당 위치에 조이스틱 생성
- 터치 시작점을 기준으로 이동 계산

초기 기본값은 고정형으로 설정한다.

## 16.2. 경로 탐색

좀비는 플레이어를 발견하면 장애물을 회피하면서 접근한다.

A* 알고리즘을 사용한다.

조건:

- 대각선 이동 금지
- 벽 통과 금지
- 통과 불가능한 장애물 회피
- 플레이어 탐지 범위
- 추격 범위
- 공격 거리
- 재탐색 간격
- 경로 탐색 실패 처리

모든 좀비 AI는 서버에서 실행한다.

클라이언트마다 독립적인 AI를 실행해서는 안 된다.

다수의 좀비가 동시에 존재할 경우 경로 탐색 비용을 최적화한다.

## 16.3. 좀비 종류

### 일반 감염자

- 이동속도 보통
- 평균 HP
- 근거리 공격

### 질주 감염자

- 빠른 이동
- 낮은 HP
- 빠른 추격

### 중장갑 감염자

- 높은 HP
- 느린 이동
- 높은 방어력

### 탐지 감염자

- 넓은 탐지 범위
- 다른 감염자에게 플레이어 위치 공유

### 특수 감염자

- 고유 행동 패턴
- 특수 스킬
- 단계별 전투 패턴

### 보스 감염자

- 높은 HP
- 여러 공격 패턴
- 단계별 행동 변경
- 특정 조건에 따른 약점 노출

초기 프롤로그에는 일반 감염자와 질주 감염자를 구현한다.

# 17. 작업대 및 직업 강화

## 17.1. 작업대

스토리 맵 곳곳에 작업대를 설치한다.

플레이어가 작업대 근처에서 상호작용하면 강화 UI를 연다.

PC는 E 키를 사용한다.

모바일은 상호작용 버튼을 누른다.

## 17.2. 강화 재화

한 판 안에서 획득하는 '보급 부품'을 사용한다.

보급 부품은 몬스터 처치, 임무 수행, 아이템 획득 등을 통해 얻을 수 있다.

## 17.3. 강화 종류

- 공격력 증가
- 공격 간격 감소
- 최대 HP 증가
- 스킬 위력 증가
- 스킬 쿨타임 감소
- 특수 능력 강화

## 17.4. 강화 단계

예시:

공격력 강화:

- 1레벨: +10%
- 2레벨: +20%
- 3레벨: +30%
- 4레벨: +45%

강화 효과는 최대 단계 제한을 가진다.

소모 재화가 부족하면 강화할 수 없다.

강화 성공 시 실시간으로 능력치를 변경한다.

서버가 강화 가능 여부를 검사한다.

초기 강화 상태는 해당 게임 한 판 동안만 유지한다.

계정 레벨과 별개의 시스템으로 구현한다.

스킨 구매, 소유권, 장착 상태는 서버에서 검증한다.

모든 버튼은 손가락으로 누르기 충분한 크기를 유지한다.

- 버튼 위치
- 기본 배치 초기화
- 진동 피드백 ON/OFF

초기에는 크기와 투명도, 기본 배치 초기화를 먼저 구현한다.

위치 자유 변경은 후속 단계에서 구현할 수 있다.

기기에서 진동을 지원하지 않으면 해당 기능을 비활성화한다.

# 22. 실시간 멀티플레이

## 22.1. 핵심 원칙

**서버 권한 기반(Server Authoritative) 구조를 사용한다.**

서버가 다음 데이터를 최종적으로 결정한다.

- 플레이어 위치
- 이동 가능 여부
- 공격 판정
- 스킬 사용 가능 여부
- 좀비 AI
- 좀비 위치
- 피해량
- HP
- 아이템
- 강화
- 미션
- 게임 결과

클라이언트는 입력을 전송한다.

서버는 입력을 검증하고 게임 상태를 갱신한다.

## 22.2. 클라이언트 처리

- 입력 수집
- 캐릭터 렌더링
- 애니메이션
- UI
- 사운드
- 이동 예측
- 위치 보간
- 서버 상태 보정

서버와 클라이언트의 위치가 다르면 서버 상태를 기준으로 보정한다.

## 22.3. 네트워크 메시지

공유 TypeScript 타입으로 WebSocket 프로토콜을 정의한다.

주요 메시지:

- AUTH
- JOIN_ROOM
- LEAVE_ROOM
- PLAYER_INPUT
- ATTACK_REQUEST
- USE_SKILL
- INTERACT
- UPGRADE_REQUEST
- GAME_SNAPSHOT
- GAME_EVENT
- ERROR

각 메시지는 유형, 버전, 필요한 식별자 및 데이터를 포함한다.

모든 입력에는 적절한 유효성 검사를 적용한다.

## 22.4. 멀티플레이 요구사항

- 최대 4인
- 서로의 캐릭터 표시
- 실시간 이동
- 실시간 공격
- 공동 좀비 AI
- 체력 동기화
- 미션 공유
- 직업 스킬 동기화
- 작업대 강화
- 클리어 및 게임 오버 동기화
- 중간 연결 종료 처리
- 재접속 처리
- 방별 데이터 격리

## 22.5. 크로스 플랫폼 멀티플레이

PC와 모바일 사용자는 반드시 같은 방에 입장할 수 있어야 한다.

입력 장치만 다르고 모든 게임 규칙은 동일하다.

PC 사용자와 스마트폰 사용자는 서로의 위치, 공격, 스킬, HP, 애니메이션을 볼 수 있어야 한다.

모바일에서 세로 모드로 변경되면 해당 사용자의 입력만 중단하며 서버의 게임 진행은 계속 유지한다.

# 27. Codex 개발 지침

다음 사항을 반드시 준수한다.

1. 기존 저장소가 있다면 먼저 구조를 분석한다.
2. 저장소가 비어 있다면 프로젝트를 생성한다.
3. 이 문서를 프로젝트 전체의 요구사항 기준으로 사용한다.
4. 먼저 실행 가능한 기본 게임을 완성한다.
5. 계획만 작성하지 말고 실제 코드를 구현한다.
6. 각 개발 단계 완료 후 빌드와 테스트를 실행한다.
7. TypeScript 타입 오류를 해결한다.
8. 임시 데이터와 실제 데이터를 구분한다.
9. 서버가 필요한 기능을 프런트엔드에서 작동하는 것처럼 꾸미지 않는다.
10. 서버 권한 기반 아키텍처를 유지한다.
11. 원작의 저작권 보호 표현을 복제하지 않는다.
12. 확장 가능한 시스템을 만든다.
13. 과도한 추상화나 불필요한 패키지는 피한다.
14. 코드 품질과 실행 성능을 유지한다.
15. 기능 완성 여부를 명확히 보고한다.
16. 환경변수 및 비밀키를 소스코드에 노출하지 않는다.
17. 사용자의 허락 없이 유료 리소스를 사용하지 않는다.
18. 서버 배포가 불가능한 경우 로컬 실행 및 테스트 방법을 제공한다.
19. 모든 주요 변경사항을 문서에 반영한다.
20. 구현하지 않은 기능은 구현했다고 주장하지 않는다.

## 반드시 달성할 첫 번째 주요 목표

**PC 사용자 1명과 스마트폰 사용자 1명이 같은 게임 방에 접속해, 각자 키보드와 모바일 조이스틱으로 4방향 이동하고, 좀비를 공격하며, 스토리 임무를 함께 진행할 수 있도록 만든다.**

스마트폰은 반드시 가로 모드에서만 이용 가능해야 한다.

게임의 모든 핵심 기능이 PC와 스마트폰에서 동일하게 작동해야 한다.

이후 최대 4인 협동과 전체 프롤로그 완성으로 확장한다.

최종적으로는 계정, 서버 채널, 레벨, 상점, 스킨, 직업, 작업대, 좀비 AI, 스토리, 멀티플레이가 통합된 하나의 완성도 높은 온라인 게임을 목표로 한다.
